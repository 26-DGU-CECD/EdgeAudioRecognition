# v1.4 추가 실험 상세 분석

분석일: 2026-10-16

## 결론

현재 탐색 후보는 F1(평균 voting) / R0(즉시 출력) / I3(적응형 0.5·1초 간격) / T0(시간 확인 없음) / wait_all이다. 비용 절감 후보이며, 최종 배포 정책이나 정확도 목표 달성을 확인한 구성은 아니다.

적응형 I3는 F1/R0의 FIFO 기준 2초 내 정답 대상 304/416을 그대로 유지하면서 요청 호출을 20.71% 줄였다. 그러나 사건 오표시가 160/416(38.46%)이고 배경 알림도 4/32(12.50%)다. 검출 시간뿐 아니라 라벨의 정확성과 안정성이 다음 실험의 핵심이다.

이번 분석에서는 기존 결과를 읽고 검산했다. 새 모델 학습, 원음 재추론, 새로운 정책 설정 실행은 하지 않았다.

## 1. 적응형 간격: 비용 절감은 확인됐지만 조건이 있다

모두 R0/T0/wait_all, FIFO 기준이다.

| 결합·간격 | 2초 내 정답 | 사건 오표시 | 배경 알림 | 요청 모델 호출 |
|---|---:|---:|---:|---:|
| F1 / I1 1초 | 56.25% | 31.25% | 6.25% | 7,392 |
| F1 / I2 0.5초 | 73.08% | 39.42% | 12.50% | 14,112 |
| F1 / I3 적응형 | 73.08% | 38.46% | 12.50% | 11,190 |
| F2 / I2 0.5초 | 73.08% | 40.38% | 12.50% | 14,112 |
| F2 / I3 적응형 | 73.08% | 39.42% | 12.50% | 11,052 |

F1의 I2→I3는 단순히 전체 정답 수만 같은 것이 아니라, FIFO에서 2초를 충족한 episode의 집합도 같다. F2/R0에서도 동일하다. 이는 이번 표본에서의 관찰이며 새로운 음원에 대한 동일성 보장은 아니다.

### 숨겨지는 손실: scream 원본 1개

처리 시간을 제외한 audio_clock에서는 F1/R0의 I2 정답률 85.58%가 I3에서 84.62%로 낮아졌다. scream 원본 1개가 네 위상에서 추가 지연됐다. 이 사례는 I2에서도 처리 시간을 더하면 이미 2초를 넘기 때문에 FIFO 전체 지표에는 추가 손실로 나타나지 않았다. 따라서 '아무 성능 손실 없이 호출 감소'라고 표현하면 안 된다.

### 호출 절감의 발생 위치

F1/R0에서 요청 입력창 수를 구간별로 재계산했다. 모델 호출 수는 아래 입력창 수의 3배다.

| 구간 | I2 | I3 | 감소 |
|---|---:|---:|---:|
| 삽입 전 합성 무음 | 1,120 | 672 | 448 |
| 원음과 겹치는 입력창 | 3,136 | 2,630 | 506 |
| 원음과 겹치지 않는 끝 무음 | 448 | 428 | 20 |
| 전체 | 4,704 | 3,730 | 974 |

전체 감소 974개 중 약 48.05%는 원음과 겹치지 않는 합성 무음 구간에서 발생했다. 원음과 겹치는 창에서도 16.14%가 줄었지만, 자연 배경·다중 사건에서 같은 20.71% 절감이 재현된다고 단정할 수 없다. 이번 비교는 전체 I2 예측을 이미 계산한 cache에서 정책이 요청할 호출을 센 것이다. 이번 파일 생성에 든 실제 추론 비용이 20.71% 줄었다는 뜻은 아니다.

## 2. 오표시의 실제 내용

F1/R0/I3의 사건 오표시는 38.46%다. 이는 사건과 겹치는 입력창에서 다른 사건 라벨을 한 번 이상 표시한 비율이다. 이후 정답도 표시될 수 있고, 분류 정밀도나 시간당 오알림률과는 다르다.

| 실제 라벨 | 잘못 표시한 라벨 | 해당 오표시가 발생한 원본 group |
|---|---|---:|
| car_horn | gun | 5/8 |
| dog_bark | cry | 4/8 |
| fire_alarm | siren | 4/8 |
| glass_breaking | gun | 4/8 |
| baby_cry | cry | 3/8 |
| bicycle | glass_breaking | 3/8 |

배경 원본 8개 중 1개에서도 fire_alarm 표시가 발생했다. 이 패턴은 클래스별 혼동과 부분 입력창의 영향을 조사해야 한다는 근거다. 표만으로 모델 오류인지 원본 라벨·사건 시점 문제인지 확정할 수는 없다.

`F1_R0_I3_오표시_원음목록.csv`에 실제 WAV 경로와 group별 오표시를 저장했다. 이 목록으로 원음 라벨과 사건 시작 위치를 우선 확인할 수 있다. 모델 예측만을 근거로 원본 라벨을 바꾸면 안 된다.

## 3. R2: 오표시는 줄지만 중요한 사건을 늦추거나 놓친다

같은 F1/I3/T0/FIFO 조건에서 R0→R2를 비교했다.

| 항목 | R0 | R2 |
|---|---:|---:|
| 전체 2초 내 정답 | 73.08% | 57.69% |
| 사건 오표시 | 38.46% | 10.58% |
| 배경 알림 | 12.50% | 12.50% |
| fire_alarm 2초 내 정답 | 20/32 | 0/32 |
| knock 2초 내 정답 | 12/32 | 8/32 |

R2에서 fire_alarm을 전혀 검출하지 못했다는 뜻은 아니다. 32 episode 중 20개는 2초를 넘겨 검출했고 12개는 관찰 구간에서 검출하지 못했다. 이 클래스에서 검출 시간의 중앙값은 검출 사례만 계산하면 약 2.011초다.

knock은 R2에서 20/32 episode를 관찰 구간 전체에서도 검출하지 못했다. 현재 policy-fit에 knock 보정 표본이 없는 문제와 함께 봐야 한다. R2를 전체 라벨에 대한 최종 정책으로 채택하기에는 근거가 부족하다.

## 4. 시간 확인: 오표시와 지연 사이 손익이 크다

F1/R0/I3/FIFO 조건이다.

| 시간 확인 | 2초 내 정답 | 사건 오표시 | 배경 알림 |
|---|---:|---:|---:|
| T0 즉시 | 73.08% | 38.46% | 12.50% |
| T1 연속 2회 | 38.94% | 16.35% | 0/32 |
| T2 라벨·점수에 따른 확인 | 40.14% | 25.72% | 0/32 |

T1/T2는 이번 소표본의 배경 알림을 없앴지만 2초 내 정답률이 크게 낮아졌다. 배경 알림 0/32는 원본 8개에서의 관찰이며 일반적인 오알림 0% 보장이 아니다. 지금 구현을 전 라벨의 기본값으로 적용하기 어렵다.

### 추가로 확인한 T2의 시간 경계 민감도

T2는 추론 완료 시각의 차이로 '0.5초 이상 확인했는가'를 계산한다. 일정한 0.5초 입력 간격이어도 모델 처리 시간 차이 때문에 완료 시각 간격은 0.499655초처럼 0.5초보다 조금 작아질 수 있다. 이런 경우 다음 결과까지 확정이 미뤄질 수 있다.

audio_clock에서는 duration_confirmed였지만 FIFO에서는 hold_or_wait로 남은 0.49~0.5초 경계 사례가 T2의 8개 설정을 합해 880개 window였다. 그중 845개 window에서는 표시 라벨 또는 표시 유무도 달랐다. 이는 독립 원본 880개를 뜻하지 않는다.

따라서 T2의 audio_clock과 FIFO 차이는 단순히 최종 시간에 11ms를 더한 효과만이 아니다. 상태 전이도 달라진다. 다만 T2 성능 손실 전부가 이 현상 때문이라고 단정하지 않는다. 후속 실험에서는 확인 근거 시간을 음원 시각으로 볼지 완료 시각으로 볼지 명시하고, 처리 시간 변동에 대한 민감도를 별도로 평가해야 한다.

## 권장 후속 작업

1. F1/R0/I2/T0를 성능 기준선, F1/R0/I3/T0를 비용 절감 후보로 유지한다. F2는 라벨별 성능 차이를 확인하는 비교군으로 남긴다.
2. 오표시 원음 목록에서 car_horn→gun, fire_alarm→siren, 배경→fire_alarm을 우선 청취하고 실제 라벨·사건 시작 시각을 확인한다.
3. 별도 policy-fit 원본에 연속 입력창을 만들어 임계값을 보정한다. knock 보정 표본을 확보하고 중요 경보별 허용 검출 손실을 사전에 정한다. 현재 evaluation 원본을 보정에 재사용하지 않는다.
4. T2 확인 시간의 기준을 명시하고 시간 변동에 대한 비교를 추가한다. 이 과정의 정책 선택에는 별도 개발 데이터를 사용한다.
5. 정책을 고정한 뒤 새로운 자연 배경·독립 사건 음원과 실제 동시 worker/UI 로그에서 검증한다. 호출 수 절감과 실제 GPU 시간·전력 절감을 구분해 측정한다.
